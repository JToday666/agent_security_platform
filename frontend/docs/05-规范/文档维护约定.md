# 文档维护约定

本文档约定前端相关事实应该写在哪里，以及文档更新时需要遵守的边界。

## 1. 文档分工

### 1.1 `frontend/README.md`

适合维护：

- 当前技术栈与能力边界
- 运行命令
- 环境变量说明
- 命名规范
- 文档索引

不适合维护：

- 复杂业务链路
- 单个模块的详细逻辑
- 跨端字段语义说明

### 1.2 `frontend/docs/`

适合维护：

- 前端分层
- 路由、布局、导航
- 模块职责
- composable / store / 门面层 / 适配层的复杂逻辑
- 关键调用链

不适合维护：

- 与后端共享的接口字段真相源
- 与视觉实现强绑定、经常变化的大段样式细节

### 1.3 `share/`

适合维护：

- API 路径
- 请求参数
- 响应结构
- 跨端字段语义
- 补充契约说明

前端文档引用这些事实时，应链接到 `share/`，不要整段复制。

## 2. 单点维护原则

同一个事实只能有一个主维护位置。

例如：

- “`/agents/submit-meta` 返回哪些字段”应主维护在 `share/`
- “提交页如何消费 submit-meta 并初始化表单”应主维护在 `frontend/docs/`
- “如何运行前端开发环境”应主维护在 `frontend/README.md`

其他文档如需提及，应使用简述 + 链接，而不是复制粘贴整段内容。

## 3. 文档深度原则

文档默认按两层深度来写：

- 宏观层
  写模块职责、目录关系、页面入口、数据流
- 微观层
  只深入重要或复杂逻辑，例如：
  - Store 状态与方法
  - composable 的编排流程
  - API 门面与 live/mock 分流
  - 路由守卫与运行时工具
  - 状态机和轮询规则

普通展示组件默认只写：

- 用途
- 输入输出
- 依赖关系

不逐行解释视觉实现。

## 4. 更新触发条件

出现以下变化时，应评估是否同步前端文档：

- 新增或删除页面
- 路由结构、布局结构、导航结构变化
- 新增重要业务模块
- Store / composable / API 门面出现新的关键职责
- Mock / Live 切换规则、运行时配置、环境变量变化
- 共享 UI 分类或使用边界发生明显变化

## 5. 写作与校对要求

- 文件名、目录名、路由名、模块名、环境变量名必须以当前仓库真实内容为准
- 若 README 中写的是未来规范，必须明确标出“当前历史例外”
- 文档中不要把理想化命名当成当前事实写入模块说明
- 增加链接后，至少定向检查一次相对路径是否可达
- 新增链路说明时，优先使用调用顺序描述，避免只列目录树不讲关系

## 6. 本仓库对 docs 的边界说明

- 仓库根 `docs/**` 默认禁止修改，除非任务明确授权
- `frontend/docs/**` 是前端内部文档目录，本类前端任务可按用户明确指令新增或维护
- `backend/docs/**` 仍属于后端范围，不在前端文档任务内修改
