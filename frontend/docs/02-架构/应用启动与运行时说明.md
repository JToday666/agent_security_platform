# 应用启动与运行时说明

本文档说明前端应用如何启动、运行时如何决策真实 API / Mock API，以及全局未授权链路如何工作。

## 1. 启动入口

应用的实际入口是 `src/main.ts`。

启动顺序如下：

1. `createApp(App)`
   创建 Vue 应用实例
2. `createPinia()`
   创建 Pinia 状态容器并挂载到应用
3. `useUserStore(pinia)`
   在应用挂载前先拿到用户 Store
4. 注册全局 `unauthorized` 事件监听
   统一处理 401 未授权场景
5. `await userStore.restoreLogin()`
   在路由真正接管页面前恢复登录态，避免刷新后被路由守卫误判为未登录
6. `app.use(router)` 与 `await router.isReady()`
   挂载路由并等待初始路由解析完成
7. `app.mount("#app")`
   最终挂载页面

这种顺序的目的很明确：

- 登录恢复优先于页面导航，避免工作台路由刷新后直接被弹回首页
- 401 事件在入口统一处理，而不是散落到每个 API 调用点

## 2. 根组件与全局登录弹窗

`src/App.vue` 只有两项职责：

- 渲染当前路由页面
- 全局挂载 `src/modules/account/components/LoginDialog.vue`

这意味着：

- 登录弹窗不是某个页面的局部能力，而是应用级能力
- 路由守卫、首页按钮、详情页按钮都可以统一调用 `userStore.openLoginDialog()`

## 3. API 运行时配置

### 3.1 基础配置

`src/shared/api/config.ts` 负责从环境变量读取运行时配置：

- `ApiConfig.baseUrl`
  默认取 `VITE_API_BASE_URL`，未配置时回退到 `/api/v1`
- `ApiConfig.enableApiMock`
  读取 `VITE_ENABLE_API_MOCK === "true"`

这个配置会被模块 API 门面层直接消费：

- 数据集模块根据它选择真实接口还是前端 Mock 数据
- 评测模块根据它选择 live-evaluation-api 还是 mock-evaluation-api

### 3.2 开发代理

`vite.config.ts` 负责两件关键事：

- 定义 `@ -> ./src` 别名
- 在开发环境把 `/api`、`/uploads` 转发到 `VITE_BACKEND_TARGET`

因此本地联调通常不需要改业务代码里的请求地址，只需要调整环境变量。

## 4. 全局 HTTP 基础设施

`src/shared/api/http-client.ts` 是所有真实 HTTP 请求的统一底座。

它做了四类关键工作：

### 4.1 请求拦截

- 从 `localStorage` 读取 `STORAGE_KEYS.user.token`
- 若 token 存在，则自动写入 `Authorization: Bearer ...`

### 4.2 响应包裹转换

后端统一响应为 `{ code, data, message }`。前端把它转换成：

- `success`
- `data`
- `message`
- `code`

业务模块不用重复解析 envelope。

### 4.3 错误归一化

`http-client.ts` 会统一提取：

- 标准 message
- 新版校验错误数组
- 旧版 `detail` 风格校验错误
- HTTP status 与业务 code

这样业务层只需要处理 `Error.message`，不需要逐个接口重写报错解析。

### 4.4 401 未授权事件

当响应状态为 401 时，`http-client.ts` 会派发：

```text
window.dispatchEvent(new CustomEvent("unauthorized", ...))
```

`src/main.ts` 监听到该事件后会：

1. 保存当前页作为登录后回跳地址
2. 清理本地鉴权状态
3. 打开登录弹窗
4. 若当前不在首页，则跳转首页
5. 若之前确实已有登录态，则提示登录状态失效

这里把“请求层发现未授权”和“页面层决定如何处理未授权”做了清晰分离。

## 5. 共享运行时工具

### 5.1 `src/shared/api/api-runtime.ts`

职责：

- 判断一个地址是否已经是绝对 HTTP URL
- 当后端返回相对资源路径时，基于 `ApiConfig.baseUrl` 推断 origin，并补成可展示 URL

这个工具当前主要服务头像和其他上传资源地址的展示。

### 5.2 `src/shared/api/memory-cache.ts`

职责：

- 读缓存、写缓存
- 对异步请求做简单并发去重

当前典型使用点：

- 数据集目录与详情
- 提交元数据 `submit-meta`

### 5.3 `src/shared/lib/asset-display-url.ts`

职责：

- 为已存在的资源 URL 追加 `?v=` 参数
- 配合头像更新后的版本号刷新浏览器缓存

### 5.4 `src/shared/constants/storage-keys.ts`

职责：

- 统一维护 `localStorage / sessionStorage` 的键名
- 集中管理用户 token、登录后回跳地址、Mock 评测记录、会话滚动位置

## 6. Mock 与真实后端的切换原则

当前切换策略不是在页面层判断，而是在模块 API 门面层判断。

例如：

- `src/modules/evaluation/api/evaluation-api.ts`
- `src/modules/dataset/api/dataset-api.ts`

门面层对页面暴露稳定接口，内部再根据 `ApiConfig.enableApiMock` 分流到：

- 真实 HTTP 实现
- 前端本地 Mock 实现

这样页面层和大部分 store / composable 不需要知道当前到底走哪一套底层。
