# 响应与错误码约定

本文档是后端统一响应包裹和稳定错误码的主维护文档。

当前统一 envelope 的实现入口为：

- `app.platform.http`
- `app.platform.schemas`
- `app.platform.exception_handlers`
- `app.platform.i18n`

## 1. 成功响应包裹

业务成功统一使用：

```json
{
  "code": 0,
  "data": {},
  "message": "success"
}
```

约定：

- `code = 0` 表示成功
- `data` 可以是对象、数组、字符串、数字或 `null`
- `message` 默认使用 `success`

## 2. 失败响应包裹

业务失败统一返回：

```json
{
  "code": 1000,
  "data": null,
  "message": "错误描述"
}
```

当前实现中：

- `app.platform.errors` 中的 `DomainError` 及其子类会返回 `{ code, data, message }`
- `RequestValidationError` 会被统一转换为 envelope，字段错误明细放在 `data.errors`
- `HTTPException` 会被兜底转换为 envelope；若 `detail` 已包含 `{ code, message, data }` 则沿用，并可通过 `messageKey` / `messageParams` 进入翻译入口
- 非结构化 `HTTPException(detail="...")` 第一阶段保留原 detail，但仍经过统一翻译入口作为兼容 fallback
- 根路径、`/api/`、`/api/v1/` 这类元信息接口也统一返回 envelope

## 3. 语言协商与响应头

后端 origin 只使用 `X-App-Locale` 决定响应语言：

```text
X-App-Locale -> zh-CN
```

规则：

- 支持语言为 `zh-CN`、`en-US`、`fr-FR`、`es-ES`、`ja-JP`
- 缺失或不支持 `X-App-Locale` 时统一回退 `zh-CN`
- `Accept-Language` 不直接影响后端响应；它只作为前端或网关首次猜测语言的输入来源
- 如果前端或网关希望按浏览器语言分流，必须先把 `Accept-Language` 归一化为 `X-App-Locale`
- JSON 响应统一返回 `Content-Language: <normalized-locale>`
- JSON 响应统一包含 `Vary: X-App-Locale`；已有 `Vary` 时追加，不覆盖
- 非 JSON 静态资源不强制添加语言响应头

这样做是为了让缓存维度只围绕归一化后的应用语言展开，避免浏览器原始 `Accept-Language` 的长字符串组合污染共享缓存。

## 4. 当前稳定错误码

以下错误码均为当前实现已返回或已被测试覆盖的口径。

| code    | HTTP       | 适用范围                                                    | 含义                                       |
| ------- | ---------- | ----------------------------------------------------------- | ------------------------------------------ |
| `0`     | 200        | 全部成功响应                                                | 成功                                       |
| `1000`  | 400 或 422 | 通用参数校验失败                                            | `ValidationDomainError` 或请求参数校验失败 |
| `1001`  | 401        | `POST /api/v1/auth/login`                                   | 用户名或密码错误                           |
| `1002`  | 409        | `POST /api/v1/auth/register`                                | 用户名或邮箱已被注册                       |
| `1003`  | 409        | `PUT /api/v1/user/profile`                                  | 用户名已被占用                             |
| `1004`  | 403        | `PUT /api/v1/user/profile`                                  | 邮箱不可修改                               |
| `500`   | 500        | 显式构造的 `DomainError` 场景                               | 例如头像写文件失败                         |
| `40002` | 400        | Agent 注册 / 评测提交校验                                   | 提交参数校验失败                           |
| `40100` | 401        | 需要登录的业务接口                                          | 未登录或登录失效                           |
| `40300` | 403        | 评测详情 / 动作接口                                         | 无权访问他人任务                           |
| `40400` | 404        | 数据集详情 / 评测详情                                       | 目标不存在                                 |
| `40900` | 409        | 评测提交接口                                                | `requestId` 已被不同请求体使用             |
| `40901` | 409        | Agent 验证 / 归档 / 评测提交 / 评测动作接口                 | 当前状态不允许该动作                       |
| `40902` | 409        | 评测动作接口                                                | 已达到暂停次数上限                         |
| `40903` | 409        | `POST /api/v1/evaluations/{evaluationId}/score/recalculate` | 评测尚未结束，不能计算评分                 |
| `40904` | 409        | `POST /api/v1/evaluations/{evaluationId}/score/recalculate` | 评测没有可评分样本                         |
| `40910` | 409        | `POST /api/v1/difficulty/versions/recalculate`              | 难度版本编号已存在                         |
| `50000` | 500        | 全局未捕获异常                                              | 服务内部错误                               |

说明：

- `500` 只来自显式构造的 `DomainError`
- 未捕获异常的全局兜底统一返回 `50000`
- 当前文档不收录“模型预留但未实际返回”的占位 code

## 5. 鉴权失败口径

当前 `get_current_user` 的失败口径如下：

- 未携带 Bearer token：`40100`，消息为 `未登录或登录已失效。`
- token 无效或过期：`40100`，消息为 `未登录或登录已失效。`
- token 解析成功但用户不存在：`40100`，消息为 `未登录或登录已失效。`

## 6. 参数校验失败示例

```json
{
  "code": 1000,
  "data": {
    "errors": [
      {
        "field": "email",
        "reason": "字段值不合法。"
      }
    ]
  },
  "message": "请求参数校验失败"
}
```

## 7. 后续国际化治理目标

当前第一阶段不改变响应 body 契约，只把运行时基础设施和首批后端生成文案接到统一入口。后续目标是逐步收敛到更标准的治理形态：

- 业务异常继续以稳定 `code` 为判断依据，新增后端文案必须提供稳定 message key
- 普通 `HTTPException(detail="...")` 逐步迁移为 `DomainError` 或结构化 `detail`
- 可选增加 `messageKey` / `messageParams` / `reasonKey` / `reasonParams`，但不能成为旧前端的必需字段
- 数据库 metadata translations、导入导出入库、历史评测展示 enrich、缺词观测和翻译质量流程分阶段落地
