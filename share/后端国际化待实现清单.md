# 后端国际化待实现清单

## 0. 当前进度快照

截至 2026-05-15，首期后端运行时国际化链路已经基本打通，API envelope 仍保持 `{ code, data, message }` 不变。

已完成内容：

- 平台层已新增统一 i18n 入口，支持 `zh-CN`、`en-US`、`fr-FR`、`es-ES`、`ja-JP`，并完成 locale 别名归一化、`ContextVar` 请求上下文、消息目录加载、fallback 与参数插值。
- 后端 origin 只认 `X-App-Locale`；缺失或不支持时回退 `zh-CN`。`Accept-Language` 不直接影响后端响应，只作为前端或网关生成 `X-App-Locale` 的输入来源。
- FastAPI 应用已注册 locale middleware，JSON 响应已补 `Content-Language` 与 `Vary: X-App-Locale`，非 JSON 静态资源不强制追加语言响应头。
- `DomainError` 及子类已支持 `message_key` / `message_params`；全局异常处理器已覆盖业务异常、FastAPI/Pydantic 请求校验错误、结构化 `HTTPException`、非结构化 `HTTPException` 兼容 fallback 和兜底异常的本地化入口。
- 后端消息目录已包含 5 种语言的首批业务错误、校验错误、Agent 模板、评测状态和排行榜匿名名。
- Agent 模板已改为内部模板字典，在返回 `AgentTemplate` 时按当前 locale 生成 `name`、`description`、`tags`；Agent 常见错误与默认验证失败提示已接入翻译入口。
- Dataset catalog/detail 服务层已接入翻译映射，具备按 locale 返回分类、子类和 display meta 展示字段的服务层能力。
- Evaluation 已覆盖提交预检 warning、提交校验错误、`progress.statusText`、动作冲突和幂等冲突等后端生成文案。
- Leaderboard 匿名展示名、排行榜不存在错误，以及 Auth/User/Scoring/Difficulty 常见业务错误已接入翻译入口。
- metadata JSON dataclass 已增加 `translations` 字段，文件级 `load/write` 已支持 translations round-trip，空 translations 写出时会省略。
- 已补充定向测试；验证入口见本文第 7 节和 `backend/README.md`。

尚未完成内容：

- 数据库层翻译模型还未落地：ORM、Alembic、真实表结构、导入入库和数据库导出仍未完整支持 translations。
- `DatasetRepository.load_translation_maps()` 的真实数据库查询还未实现，当前 Dataset 服务层能力依赖仓储支持。
- 历史评测中的 `datasetNames`、报告 `summary.byRiskCategory[].name` 仍需要按当前 locale 展示时 enrich，旧快照字段只作为 fallback。
- metadata 真源 `data/metadata/**` 的实际翻译内容还未系统补齐，当前只是结构支持。
- 前端或网关基于 `Accept-Language` 生成 `X-App-Locale` 的 bootstrap 策略、前端 `http-client` 兼容 `data.errorKey/params`、评测详情/排行榜缓存 key 带 locale、前端硬编码治理仍未进入本清单的实现阶段。
- CI 硬编码扫描、伪本地化、翻译质量治理和缺词观测还未落地。

下一步建议先解决“数据库翻译模型与读取链路”，再处理“历史快照展示 enrich”，最后推进“前端兼容增强与质量治理”。这样能先把后端首期链路从测试 stub 推到真实数据闭环，避免过早扩散到前端和质量平台。

全项目国际化现状校准：

- 前端运行时国际化基础已经完整接入：支持 5 种 locale，具备 locale 路由前缀、语言切换、懒加载语言包、`document.documentElement.lang`、localStorage 语言缓存、运行时翻译器和按 locale 拆分的部分接口缓存 key。

- 后端 API 语言选择只以 `X-App-Locale` 为准，忽略 `Accept-Language`；因此真实后端语言链路依赖前端先把当前应用语言写入 `X-App-Locale`。
- 后端运行时语言包结构完整：`backend/app/platform/i18n/messages/*.json` 中 5 个 locale 的 key 集合一致；当前每个 locale 62 个 key。

- 前端仍保留若干空语言域文件，例如 `charts.json`、`errors.json`、`validation.json`；它们不是功能错误，但属于后续语言资源整理项。
- 数据集真实内容仍是当前最大缺口：`data/metadata/**` 尚未系统补齐 translations，ORM/Alembic/导入入库/数据库导出未完整支持，`DatasetRepository.load_translation_maps()` 尚未实现真实查询。

下一步国际化目标校准：

- 第一目标是闭合真实 API 语言链路：前端启动前确定 locale，所有真实请求稳定携带 `X-App-Locale`，切换语言后不会复用上一语言的后端内容缓存。
- 第二目标是关闭“服务层有接口、仓储无实现”的缺口：落地数据库 translations 字段、导入导出 round-trip 和 `DatasetRepository.load_translation_maps()`。
- 第三目标是补齐官方内容翻译：系统补齐 `data/metadata/**` 中分类、子类、display meta、resources label、media title/description 等官方展示字段的 5 语言内容。
- 第四目标是处理历史展示 enrich：评测历史快照、报告摘要、排行榜展示等按当前 locale enrich，旧快照字段只作为 fallback。
- 第五目标是治理 mock 与前端兼容：明确 mock 是否继续保留；若保留，需要按 locale 返回 mock 内容；若不保留，应关闭并删除可达 mock 分支，同时让前端兼容未来可选 `messageKey/messageParams`。
- 第六目标是质量治理：加入缺词观测、定向硬编码扫描、伪本地化和翻译评审流程，但不翻译用户输入、原始样本、审计证据和外部系统原文。

后续目标总览：

- 数据库 translations：补 ORM、Alembic、导入入库、数据库导出和真实查询闭环。
- metadata 内容补齐：系统补齐 `data/metadata/**` 的多语言内容，并保持 JSON round-trip 幂等。
- 历史展示 enrich：评测历史快照、报告摘要和排行榜展示字段按当前 locale enrich，原始证据和用户输入不翻译。
- 前端兼容增强：可选支持 `messageKey/messageParams`、按 locale 拆缓存 key，并由前端或网关把 `Accept-Language` 归一化为 `X-App-Locale`。
- 质量治理：缺词观测、硬编码扫描、伪本地化、翻译评审和发布流程。

## 1. 目标与边界

后端国际化只负责后端生成、维护或持久化的用户可见文案，不负责前端页面文案。

后端负责的内容包括：

- 业务错误 message
- 请求校验提示
- 数据集目录与详情展示字段
- 内置 Agent 模板与验证提示
- 评测详情、报告、排行榜的展示字段
- 官方元数据的多语言返回

前端继续负责：

- 页面标题、按钮、表单、空状态、布局提示、组件文案
- 浏览器侧格式化与 UI 语言切换

不纳入后端翻译范围：

- 用户输入内容
- 稳定协议字段，例如 code、ID、路由、请求字段名、响应字段名、枚举值
- 原始样本、Agent 原始响应、Oracle 原始输出、执行日志、审计证据、外部系统原文
- 代码注释、数据库注释、开发排查日志

第一阶段不修改现有响应 envelope：`{ code, data, message }` 保持不变，前端继续只读 `message` 和稳定 `code` 即可。

## 2. 统一语言规则

### 2.1 支持语言

| Locale  | 说明       |
| ------- | ---------- |
| `zh-CN` | 默认语言   |
| `en-US` | US English |
| `fr-FR` | 法语       |
| `es-ES` | 西班牙语   |
| `ja-JP` | 日语       |

### 2.2 解析规则

后端 origin 只认归一化后的 `X-App-Locale`，不直接使用浏览器原始 `Accept-Language` 决定响应语言：

```text
X-App-Locale -> zh-CN
```

`Accept-Language` 仍有价值，但它的职责前移到前端或网关：首次进入应用、未登录或没有用户语言设置时，可以读取浏览器 `Accept-Language`，按支持语言表归一化后写入 `X-App-Locale`。这样后端缓存维度只依赖归一化后的应用语言，而不是浏览器原始语言列表。

### 2.3 归一化规则

```text
zh / zh-Hans / zh-Hans-CN / zh-CN -> zh-CN
en / en-US / en-GB -> en-US
fr / fr-FR / fr-CA -> fr-FR
es / es-ES / es-MX -> es-ES
ja / ja-JP -> ja-JP
其他 -> zh-CN
```

前端或网关如需使用 `Accept-Language`，应按 q-factor 取首个可支持的语言，再归一化为上述支持集，并写入 `X-App-Locale`。后端 origin 不直接把浏览器原始 `Accept-Language` 当作响应变体来源。

### 2.4 fallback 规则

- 解析失败或不支持时，回退 `zh-CN`
- 单个字段缺翻译时，先回退到该实体的中文 canonical 字段
- 整个实体缺翻译时，仍返回中文 canonical 对象，不返回半空对象
- 中文 canonical 也缺失时，回退到稳定 `code` 或安全占位文案
- 任何缓存、预热、导出和 worker 任务如果会生成可见文本，都必须显式带 locale 或默认 `zh-CN`

### 2.5 响应头

- JSON 响应的 `Content-Language` 返回归一化后的 locale
- Origin 统一使用 `Vary: X-App-Locale`
- `Accept-Language` 只作为前端或网关的 bootstrap 输入，不作为 Origin 的缓存维度
- 如果边缘层需要按 `Accept-Language` 分流，必须先在边缘做归一化，再写入 `X-App-Locale`
- 非 JSON 静态资源不强制追加语言响应头

## 3. 运行时基础设施

### 3.1 Locale 中间件与请求上下文

- 建立唯一 locale 解析入口，禁止 service、repository、mapper 再次读取 header
- 在 middleware 中解析 `X-App-Locale`，写入 `ContextVar`
- `Accept-Language` 不在后端 middleware 中参与响应语言选择；如需使用，应由前端或网关先归一化成 `X-App-Locale`
- 使用 `try...finally` 严格 reset token，避免并发串语言
- 提供 `get_current_locale()` 或等价 helper，供异常处理器、service 和 formatter 读取
- 在 `backend/app/main.py` 的应用初始化阶段注册 middleware，确保路由和异常处理器都能读取到 locale
- 非 HTTP 场景（worker、脚本、导入任务、测试工具）支持显式 locale 参数，默认 `zh-CN`

### 3.2 翻译目录与加载器

- 建立后端语言资源目录，例如 `backend/app/platform/i18n/messages/{locale}/`
- 按 namespace 拆分短文案，例如 `common`、`errors`、`validation`、`datasets`、`agents`、`evaluations`、`leaderboard`
- 翻译加载支持缓存、参数插值、缺词 fallback 和 missing key 日志
- 翻译接口只接收稳定 key + params，不在业务代码中拼接用户可见句子
- 为错误码、异常类和字段 reason 维护稳定映射表，避免把中文硬编码散落到各处

### 3.3 统一响应头与响应封装

- 统一在 JSON 响应处补 `Content-Language`
- 所有 JSON 响应都带 `Vary: X-App-Locale`
- 文件下载、报告导出等非 JSON 响应不默认追加语言响应头；如果未来返回可展示的本地化文件内容，需要单独定义下载契约和缓存策略
- 如果未来增加服务端缓存，缓存 key 也必须包含 locale

### 3.4 错误本地化

- `DomainError` 及子类按 locale 返回 `message`
- `ValidationDomainError` 和 FastAPI `RequestValidationError` 的顶层 `message` 与字段 `reason` 都要本地化
- `RequestValidationError` 建立 Pydantic `type` 到翻译 key 的映射，必要时再用 `ctx` 做插值
- `HTTPException` 若携带结构化 `detail`，优先按结构化内容翻译；非结构化 detail 第一阶段保留原文，并经过统一入口作为兼容 fallback
- 未捕获异常返回本地化的安全兜底 message，同时保留 `errorType`
- 保持 `code` 稳定，不把翻译后的 message 作为前端判断条件
- 可选新增 `messageKey` / `messageParams` / `reasonKey` / `reasonParams`，但它们只能是兼容增强，不能变成前端必需字段

## 4. 官方内容本地化

### 4.1 数据集元数据与数据库实体

- `data/metadata/registry/*.json` 与 `data/metadata/display_meta/*.json` 增加 `translations`
- `risk_categories` 增加 `translations JSONB NOT NULL DEFAULT '{}'`
- `risk_subtypes` 增加 `translations JSONB NOT NULL DEFAULT '{}'`
- `risk_subtype_display_meta` 增加 `translations JSONB NOT NULL DEFAULT '{}'`
- 如后续需要，`dataset_sources`、`attack_delivery_types`、`asset_types` 也按同一模式扩展
- 导入/导出脚本必须支持 translations 的 round-trip，不得只写入中文 canonical 字段
- 读取时按字段级 fallback，不返回半空对象，不把请求时翻译结果写回数据库

示例结构：

```json
{
  "code": "confidentiality",
  "name": "机密性",
  "meaning": "敏感信息保护与最小暴露。",
  "description": "面向验证码、身份信息、密码与访问密钥等敏感数据保护的风险大类。",
  "translations": {
    "en-US": {
      "name": "Confidentiality",
      "meaning": "Sensitive information protection with minimal exposure.",
      "description": "A major risk category for protecting sensitive data such as verification codes, identity information, passwords and access keys."
    }
  }
}
```

`display_meta` 中的 `translations` 需要覆盖 `short_description`、`full_description`、`highlights`、`scenarios`，以及 `resources.label`、`media.title`、`media.description` 等可见字段。

### 4.2 数据集接口

- 目录与详情接口返回按 locale 解析后的展示字段
- 需要本地化的字段包括：
  - `name`
  - `meaning`
  - `description`
  - `shortDescription`
  - `fullDescription`
  - `highlights`
  - `scenarios`
  - `resources.label`
  - `media.title`
  - `media.description`
- `resource URL`、`media URL`、`type`、`code`、`id`、`datasetId` 以及其他协议字段不翻译
- 历史评测中的 `datasetNames` 优先按当前 locale 解析，缺失时回退到历史快照的 canonical 值

### 4.3 Agent 模块

- 内置 Agent 模板的 `name`、`description`、`tags` 按请求语言返回
- Agent 创建、复制、验证、归档、提交校验相关的后端错误与 warning 按请求语言返回
- 后端生成的验证提示与状态提示走语言包，不直接拼接中文
- 外部 Agent 原始错误不翻译，但可在外层包一层本地化提示，并保留原文用于排查
- 用户自己填写的 Agent 名称和描述不翻译

### 4.4 评测与报告

- 提交预检 `warnings[].message` 按请求语言返回
- 评测详情 `progress.statusText` 按请求语言返回
- 评测报告 `summary.byRiskCategory[].name` 按请求语言返回
- 评测详情 `representativeSamples.*.outcomeReasonText` 按请求语言返回
- 评测动作失败提示、幂等冲突提示、状态不允许操作提示按请求语言返回
- `datasetNames`、`sampleSummary`、`score`、`status`、`publicToLeaderboard`、`leaderboardDisplayMode` 等稳定字段保持不变，只翻译展示文本

### 4.5 排行榜、评分与难度

- 排行榜匿名展示名按请求语言返回，例如中文为“匿名 Agent”，英文为“Anonymous Agent”
- 排行榜不存在、评分不存在、评测未结束、难度版本不存在等错误提示按请求语言返回
- `verificationTier`、`safetyCertification`、score model version、benchmark version、difficulty version 等稳定值不翻译
- 公共展示名来自用户/Agent 输入时保持原样，不做机器翻译

### 4.6 Auth / User / Platform

- 登录、注册、个人资料、上传、权限、未登录、登录失效、无权限等提示按请求语言返回
- `DomainError`、`AuthError`、`ForbiddenError`、`NotFoundError`、`ConflictError` 的 message 都应走统一翻译入口
- 平台兜底异常保留 `errorType`，但 message 需要按 locale 本地化
- 用户输入内容、邮箱、用户名、Agent 名称、任务备注等原文不翻译

## 5. API 影响与兼容策略

第一阶段不需要修改现有 API body 契约。

- 保持现有 envelope：`{ code, data, message }`
- 保持 `code` 作为唯一稳定判断依据
- 保持验证错误结构为 `data.errors[{ field, reason }]`
- `message` 始终返回当前请求语言下的可展示文案，旧前端继续可用
- `messageKey` / `messageParams` / `reasonKey` / `reasonParams` 作为可选增强保留，但不作为首期依赖
- 前端或网关需要保证发给后端 origin 的 canonical 语言头为 `X-App-Locale`；`Accept-Language` 只用于首次猜测和归一化，不再直接影响后端响应
- 如后续确需离线渲染或前端自主翻译，再新增专用元数据导出接口，不改现有业务接口

## 6. 下一步建议实施顺序

### 6.1 数据库翻译模型与迁移

下一步优先解决数据库层没有真实 translations 的问题。当前 Dataset 服务层已经会读取仓储提供的翻译映射，但真实 ORM、Alembic、导入入库和导出还没有闭环。

建议方案：

- 首期采用“核心字典实体 JSONB translations + display meta JSONB translations”的兼容方案，先给 `risk_categories`、`risk_subtypes`、`risk_subtype_display_meta` 增加 `translations JSONB NOT NULL DEFAULT '{}'`。
- 如果本阶段也要覆盖元数据字典展示，再同步给 `dataset_sources`、`asset_types`、`attack_delivery_types` 增加同形态字段；否则先在文档中标记为第二批。
- Alembic 迁移只做加列和默认值，不回填翻译内容，不改原 canonical 中文字段。
- ORM 字段与 dataclass 字段保持同名 `translations`，避免 importer/exporter 做额外映射。
- 回退顺序固定为：目标 locale 字段 > `zh-CN` 翻译字段 > 主表 canonical 字段 > 稳定 code。

验收重点：

- 迁移可重复在空库和已有库上执行。
- translations 为空时所有接口仍返回中文 canonical 字段。
- 单个字段缺翻译时只回退该字段，不丢弃整个实体翻译。

### 6.2 metadata importer/exporter 真实 round-trip

数据库结构落地后，继续打通 `data/metadata` 与数据库之间的多语言 round-trip。

建议方案：

- `load_metadata_bundle()` 和 `write_metadata_bundle()` 已支持文件级 translations，下一步把 `_upsert_*()` 和 `build_metadata_bundle_from_database()` 补齐到数据库字段。
- importer 写库时只写入 JSON 中明确提供的 translations，不自动机器翻译，也不把请求时 enrich 的展示结果写回数据库。
- exporter 从数据库导出时保留 translations，空 translations 可省略，保证现有 JSON 可读性。
- 对 registry 与 display_meta 分别补测试：新增导入、重复导入幂等、数据库导出后再导入不丢 translations。

验收重点：

- 同一 bundle 连续导入两次，第二次只产生 update，不产生重复行。
- 导出后的 JSON 再加载，translations 与 canonical 字段都保持一致。
- display meta 的 `resources.label`、`media.title`、`media.description` 能在 translations 中完整保留。

### 6.3 DatasetRepository 真实翻译读取

完成数据库字段后，实现真实 `DatasetRepository.load_translation_maps()`，把服务层已有能力接到数据库。

建议方案：

- 仓储方法输入保持当前服务层约定：`locale`、`category_ids`、`subtype_ids`。
- 查询只取当前页面涉及的 id，避免全量 metadata 扫描。
- 返回结构保持当前测试 stub 形态：`categories`、`subtypes`、`display_meta` 三张映射表。
- 翻译解析放在仓储或轻量 helper 中，服务层继续只做字段级 fallback 和响应组装。

验收重点：

- catalog/detail 在 `X-App-Locale: en-US` 下返回翻译字段。
- translations 缺字段时回退中文 canonical。
- 不翻译 `datasetId`、category code、URL、media type 等稳定字段。

### 6.4 评测历史快照与报告展示 enrich

真实数据集翻译可读取后，再处理评测历史展示字段。

建议方案：

- `run_datasets.dataset_name` 和 `run_reports.summary_json.byRiskCategory[].name` 保留为创建时快照，不做批量迁移。
- API 展示时优先按 `dataset_code` / `categoryId` 和当前 locale 重新 enrich；找不到翻译或实体已删除时回退历史快照字段。
- enrich 逻辑应集中在 Evaluation mapper/helper，避免列表页、详情页、报告页各自拼装。

验收重点：

- 旧评测记录无需重算即可在不同 locale 下展示不同风险分类名和数据集名。
- 原始执行证据、Agent 输出、Oracle 结果、用户输入不被翻译。
- 报告 summary 数字统计不受 locale enrich 影响。

### 6.5 前端兼容增强

后端真实数据闭环稳定后，再处理前端增强，避免前后端同时漂移。

建议方案：

- `http-client` 兼容读取未来可选的 `data.errorKey/params` 或 `messageKey/messageParams`，优先前端语言包渲染，缺 key 时回退后端 `message`。
- 前端或网关在没有用户语言设置时读取 `Accept-Language`，归一化为后端支持的 locale，并写入 `X-App-Locale`。
- 所有依赖后端本地化内容的缓存 key 必须包含 locale；重点检查评测详情、排行榜、数据集详情。
- 前端验证涉及 `pnpm`，按仓库约束由用户在 `frontend/` 手动执行。

验收重点：

- 旧后端只返回 `message` 时前端仍正常。
- 新后端返回可选 key 时前端能优先翻译。
- 切换 locale 后不会复用上一语言缓存。

### 6.6 质量治理与观测

最后再推进硬编码扫描、伪本地化和缺词治理，作为独立阶段处理。

建议方案：

- 后端 missing key 日志记录 locale、key、接口路径和实体 code。
- 增加定向硬编码扫描规则，只扫描用户可见响应与消息目录触达范围，避免把注释、日志、样本原文误报为必须翻译。
- 伪本地化先用于前端 UI 和后端短文案，不用于样本 payload、证据、用户输入或外部 Agent 原文。

验收重点：

- 缺词可定位到具体 key 和接口。
- 扫描规则不会要求翻译稳定 code、enum、路径、样本和审计证据。
- 翻译质量治理不阻塞首期兼容链路上线。

## 7. 验收标准

- 不带语言头时，接口默认返回中文
- 仅带 `Accept-Language` 时，后端仍默认返回 `zh-CN`
- 有效 `X-App-Locale` 决定后端响应语言
- 不支持的 `X-App-Locale` 回退 `zh-CN`
- 不支持语言时，后端回退 `zh-CN`
- 响应包含 `Content-Language`
- Origin 响应包含 `Vary: X-App-Locale`
- `code`、`data`、字段名、ID、路由、enum value 不被翻译
- 旧前端只读取 `message` 仍能正常展示错误
- FastAPI 校验错误的 `data.errors[{field,reason}]` 结构保持不变
- 数据集 catalog/detail、Agent 模板、评测预检、评测详情、报告与排行榜匿名展示都能按 locale 返回
- translations 缺失时按字段级 fallback 回退中文，不影响接口结构
- 导入/导出与数据库迁移可重复执行，translations round-trip 保持幂等
- 缺词可以观测，能够记录 locale、key、实体 code 和接口路径

## 9. 风险与补充约束

- 不翻译用户输入、原始样本、执行证据、审计日志和外部系统原文
- 不在业务代码里拼接用户可见中文，统一走翻译接口
- 不把 messageKey 当成前端必需字段，避免首期改动扩大
- 任何缓存、CDN、网关和 worker 结果都必须把归一化后的 `X-App-Locale` 当作维度之一，不直接使用原始 `Accept-Language` 作为后端缓存维度
- 如果后续 translations 复杂度继续上升，再评估单独翻译表或导出接口，不要提前扩大首期范围
