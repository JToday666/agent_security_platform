# 智能体安全评测平台国际化工程指导方案

## 1. 建设目标

国际化是平台级工程能力，不是一次性的页面翻译。平台需要在保持评测可信度、接口稳定性、证据可审计和工程可维护的前提下，逐步建立多语言界面、多语言业务展示、多语言错误反馈、多语言报告展示和多语言质量治理能力。

初始支持语言固定为：

| Locale  | 语言               |
| ------- | ------------------ |
| `zh-CN` | 简体中文，默认语言 |
| `en-US` | US-English         |
| `fr-FR` | 法国法语           |
| `es-ES` | 西班牙西班牙语     |
| `ja-JP` | 日语               |

以下专有名词在所有语言中保留英文：

```text
AEGIS
Agent
API
Docker
Oracle
```

国际化覆盖平台展示层和官方业务展示内容，包括导航、页面文案、表单、状态、图表、错误反馈、数据集展示字段、风险分类、报告展示字段和必要的导出展示文本。国际化不覆盖评测样本原文、Agent 原始响应、Oracle 原始输出、执行日志、外部系统返回、用户输入内容和审计证据。

核心目标是：用户选择任一支持语言后，平台 UI、业务内容、错误反馈、排行榜、评测详情、报告和图表形成一致体验；同时评测样本、判定逻辑、结构化结果、原始证据和接口事实保持稳定、可复现、可审计。

## 2. 项目现状与总体策略

当前仓库是前后端分离的安全评测系统。前端基于 Vue 3、TypeScript、Pinia、Vue Router、Axios、ECharts 和 `vue-i18n` 依赖；后端基于 FastAPI、SQLAlchemy、PostgreSQL、Alembic 和异步 worker；跨端接口契约维护在 `share/`，官方数据集元数据维护在 `data/metadata/`。

这种结构决定国际化不能只由前端或后端单独完成：

- 前端掌握页面交互、路由、状态展示、图表渲染、表单校验和浏览器格式化，应主导 UI 文案、体验一致性和前端质量门禁。
- 后端掌握数据集、风险分类、报告摘要、业务错误和 worker 生成结果，应负责业务语义内容、错误兜底和官方元数据的本地化。
- 数据库和 metadata 是官方领域内容的运行时来源，应具备可回退、可审计、可批量导入、可缓存和避免 N+1 查询的翻译模型。
- 评测 worker 脱离浏览器上下文，评测核心和展示语言必须隔离，避免 UI 语言影响安全判定。

推荐总体架构为：

```text
前端 UI 国际化治理
+ 后端业务语义本地化
+ 官方 metadata 翻译源
+ 数据库实体翻译表
+ URL 承载展示语言
+ API Header 传递内容语言
+ 错误双轨协议
+ 评测核心与展示语言隔离
+ CI 质量门禁
```

不采用以下长期方案：

| 方案                                         | 结论           | 原因                                                                 |
| -------------------------------------------- | -------------- | -------------------------------------------------------------------- |
| 全部由前端翻译                               | 不采用         | 数据集、风险分类、报告、错误和导出内容会复制到前端，后端业务语义缺失 |
| 全部由后端翻译                               | 不采用         | SPA 的导航、表单、图表、组件状态和交互反馈会被后端牵制               |
| 核心实体直接使用多语言 JSON 字段作为唯一模型 | 不作为长期方案 | 搜索、排序、索引、fallback、ORM 查询和批量加载复杂度高               |
| 一开始引入完整 TMS                           | 暂不采用       | 当前语言数量固定，Git + CI + review 更适合起步和审计                 |

## 3. 语言上下文模型

平台主流程使用两条语言上下文：

| 上下文          | 含义                     | 来源                               | 作用范围                                                 |
| --------------- | ------------------------ | ---------------------------------- | -------------------------------------------------------- |
| `displayLocale` | 当前浏览器 UI 展示语言   | URL、用户选择、前端状态            | 前端 UI、图表、状态 label、Toast、表单校验、时间数字格式 |
| `contentLocale` | 后端业务展示内容返回语言 | `X-App-Locale` / `Accept-Language` | 数据集展示字段、风险分类、业务错误、报告展示字段         |

两者需要分离，但通常保持同值。分离的理由是 UI 语言属于浏览器交互状态，业务展示语言属于 API 返回内容和缓存维度；明确边界后，前端可以独立治理界面体验，后端可以独立治理业务语义和 fallback。

当前阶段不把以下概念作为主流程持久字段：

| 字段               | 当前策略             | 理由                                                                                |
| ------------------ | -------------------- | ----------------------------------------------------------------------------------- |
| `taskLocale`       | 不进入评测任务主流程 | 当前没有多语言邮件、站外通知、多语言静态报告版本或需要按语言固化的异步自然语言摘要  |
| `evaluationLocale` | 不随 UI 引入         | 判定模块使用固定 prompt、固定 JSON schema 和固定结构化输出，UI 语言不得影响判定逻辑 |
| `datasetLocale`    | 不作为用户可选维度   | 当前样本语言固定，数据集是否可用与界面语言无关，样本 payload 不随 UI 语言变化       |
| `exportLocale`     | 作为未来导出任务字段 | 当前 `report_uri` 仍为预留，在线报告按当前语言动态展示；未来静态导出再固化导出语言  |

语言流转为：

```text
URL / 用户语言选择
  -> displayLocale
  -> 前端 UI、图表、状态、格式化
  -> API Header: X-App-Locale / Accept-Language
  -> contentLocale
  -> 后端业务展示字段、错误兜底、报告展示字段
```

关键约束：

- `displayLocale` 不影响 Oracle、rubric、评分逻辑和结构化判定字段。
- `contentLocale` 只影响后端返回的展示字段和兜底消息，不改变字段结构、ID、code、status 和 enum。
- 原始证据、样本 payload、Agent 响应、Oracle 输出始终保留原文。
- 在线页面按当前语言动态展示；未来离线导出按导出请求语言固化。

## 5. Locale、路由与 Header 策略

### 5.1 `displayLocale` 使用 URL 承载

前端页面路由应使用显式 locale 前缀：

```text
/{locale}/...
```

示例：

```text
/zh-CN/dataset
/en-US/leaderboard
/fr-FR/user/evaluation/{evaluationId}
/ja-JP/user/agents
```

采用 URL 前缀的理由：

- 分享链接和书签保留语言上下文。
- 刷新页面后语言稳定。
- 公开数据集、排行榜、公开报告具备未来搜索和外部传播扩展能力。
- URL、Pinia、`vue-i18n`、API Header 可以形成一致状态源。

缺少 locale 或 locale 不合法时，前端按以下顺序解析并重定向到标准路由：

```text
URL locale
> 用户显式选择
> localStorage 保存值
> 用户 profile.language，后续扩展
> 浏览器 navigator.languages
> zh-CN
```

### 5.2 `contentLocale` 使用请求头传递

后端 API 路径保持资源语义纯净，不在路径中携带 locale。前端所有 API 请求携带归一化语言：

```http
X-App-Locale: en-US
Accept-Language: en-US
```

后端识别优先级：

```text
X-App-Locale
> Accept-Language
> zh-CN
```

响应设置：

```http
Content-Language: en-US
Vary: X-App-Locale
```

缓存层不应直接 `Vary: Accept-Language`，因为浏览器原始 `Accept-Language` 可能包含复杂 q-factor，会导致缓存维度不可控。应由前端或边缘层归一化为支持语言之一，再以 `X-App-Locale` 或等价归一化 Header 作为缓存维度。

### 5.3 fallback 规则

前端、后端、导入脚本和测试用例应共享同一套语言白名单和 fallback 规则：

```text
zh / zh-Hans / zh-CN -> zh-CN
en / en-GB / en-US -> en-US
fr / fr-CA / fr-FR -> fr-FR
es / es-MX / es-ES -> es-ES
ja / ja-JP -> ja-JP
不支持语言 -> zh-CN
目标语言字段缺失 -> zh-CN
zh-CN 也缺失 -> 稳定 code 或默认占位
```

fallback 必须可观测。业务翻译缺失不能静默吞掉，应记录缺词指标、接口路径、实体 code 和目标 locale，便于后续补齐。

## 6. 前端工程策略

### 6.1 应用层目录职责

前端国际化基础设施属于应用级能力，应收口在 `src/app/i18n/`。该目录负责语言白名单、语言包入口、未来 `vue-i18n` 初始化、懒加载和语言切换副作用。模块页面只消费 `t()`、格式化工具或已适配的 view model，不直接处理语言包加载和全局副作用。

语言资源按域组织，初始建议命名空间：

```text
common
layout
auth
profile
dataset
agent
submission
evaluation
leaderboard
report
charts
notifications
errors
validation
network
```

### 6.2 路由守卫阻塞语言包加载

正式接入时，路由切换必须把语言包加载作为导航解析的一部分，而不是页面渲染后的副作用。

推荐顺序：

```text
解析 URL locale。
校验 locale 白名单。
非法 locale 重定向到默认语言。
加载目标语言包。
加载失败时回退已在内存中的默认语言或上一个可用语言。
原子化提交全局副作用：i18n locale、Pinia locale、axios header、html lang、组件库 locale。
放行页面渲染。
```

这样可以避免页面短暂显示 `dataset.catalog.title` 这类 key 原文、中文闪烁或图表旧语言残留。

### 6.3 key 命名与防止过度复用

key 必须包含业务上下文：

```text
dataset.catalog.title
dataset.detail.sampleCount
evaluation.status.running
evaluation.detail.progressTitle
agent.status.active
leaderboard.table.rank
charts.riskDistribution.title
```

不使用无语义 key：

```text
text1
button2
pageTitle
tmpMessage
```

不要因为不同上下文中的词在中文或英文里相同，就强行抽到 `common`。不同业务域中的同一词可能在法语、西语、日语中需要不同词性、语境或语气。公共词条只承载真正跨域稳定的动作、字段和状态。

### 6.4 禁止字符串拼接

所有包含变量、数量、状态、分数、时间的用户可见文案必须使用完整 message 模板。

禁止：

```text
"当前正在评测数据集 " + datasetName
count + " 个样本"
score + " 分"
```

必须：

```text
evaluation.progress.runningDataset
evaluation.samples.count
evaluation.score.value
```

涉及复数、选择分支、状态和动态变量时使用 ICU MessageFormat 或 `vue-i18n` 等价能力。这样可以保证语序、复数、标点和空格规则由目标语言完整表达。

### 6.5 状态和枚举翻译

后端返回稳定 enum，前端翻译 label。业务逻辑不得依赖本地化文本。

示例状态：

```text
pending
running
pausing
paused
terminating
canceling
completed
terminated
canceled
failed
```

前端映射：

```text
evaluation.status.pending
evaluation.status.running
evaluation.status.completed
```

Agent 状态、提交状态、报告状态、排行榜排序项和筛选项同理。

### 6.6 ECharts 国际化

项目使用 `echarts` 和 `vue-echarts`，图表必须显式纳入国际化流程。需要覆盖：

```text
图表标题
legend
tooltip
axis label
series name
toolbox 内置文案
导出图片标题
空数据状态
错误状态
```

语言切换时，仅重新生成业务 option 不一定足够。ECharts 的内置 locale 通常在 `echarts.init()` 时传入，toolbox 等内置文案可能无法通过 `setOption` 完整切换。

规范：

- 图表 option 由当前 `displayLocale` 计算，不缓存无 locale 的展示 option。
- 语言切换后重新生成 option。
- 受 ECharts 内置 locale 影响的实例需要强制重新初始化或确认组件能完整重建。
- 销毁旧实例时必须 `dispose`，避免 Canvas/WebGL 上下文泄漏。
- 图表缓存不得跨 locale 复用。
- 图表颜色不能作为唯一信息载体，必须配合文本、图例或形状。

### 6.7 格式化工具

日期、时间、数字、百分比、持续时长和相对时间应优先使用浏览器原生 `Intl` API。当前语言数量固定，不建议为基础格式化引入 moment.js 或 dayjs 全量 locale 包。

统一封装：

```text
formatNumber
formatPercent
formatDateTime
formatDuration
formatRelativeTime
```

组件中不直接拼接：

```text
`${score}%`
`${count} 个`
`${minutes} 分钟`
```

后端统一存储和返回 UTC ISO 8601 时间；前端按 `displayLocale + 用户 timezone` 格式化。locale 不等于 timezone，英文界面用户可能在新加坡，日语界面用户也可能在美国。

### 6.8 字体、`html lang` 与文本韧性

每次切换 `displayLocale` 必须更新：

```html
<html lang="ja-JP"></html>
```

这会影响屏幕阅读器、浏览器字体选择、中日汉字字形、搜索语义和可访问性。

UI 必须承受：

```text
法语/西语长文本膨胀
日语断行
英文长词
URL
长 Agent 名称
长数据集名称
长评测 ID
长错误信息
长报告摘要
小屏宽度
```

按钮、状态 pill、徽章等原子元素不换行；错误信息、说明文本、报告结论可换行，不随意截断核心含义。中文和日文应通过 `:lang()` 与字体 fallback 区分，避免日语页面使用中文式字形。

### 6.9 IME 输入兼容

中文和日文输入法存在 composition 阶段。表单字数统计、长度限制、自动校验和提交快捷键不得在 composition 未结束时误触发。

规范：

- 监听 `compositionstart` / `compositionend`。
- 输入法组合状态中不做强制截断。
- 组合结束后再执行最终长度校验。
- 避免日文输入过程中因实时校验导致卡顿、误删或误提交。

### 6.10 前端缓存按 locale 隔离

依赖后端本地化内容的数据，缓存 key 必须包含 locale：

```text
datasets:catalog:zh-CN
datasets:detail:fr-FR:A1_identity_leakage
evaluation:detail:ja-JP:{evaluationId}
leaderboard:es-ES:{filterHash}
report:view:en-US:{evaluationId}
```

语言切换规则：

- 纯 UI 文案立即切换。
- 后端业务内容重新请求或读取对应 locale 缓存。
- 图表重新生成 option 或重建实例。
- 不把旧语言 view model 复用到新语言页面。

## 7. 后端工程策略

### 7.1 LocaleMiddleware 与 ContextVar

后端应建立统一 LocaleMiddleware，解析 `X-App-Locale` / `Accept-Language`，归一化为支持语言之一，并写入请求上下文。

FastAPI ASGI 并发环境中应使用 `contextvars.ContextVar`，并在 middleware 中用 `try...finally` 严格清理 token，避免跨请求语言污染。

规范：

```text
LocaleMiddleware 是唯一解析语言头的位置。
service、repository、mapper 不重复解析 header。
current_locale 只在请求生命周期内有效。
finally 中必须 reset token。
响应必须设置 Content-Language。
缓存响应必须设置 Vary: X-App-Locale。
```

离线 worker、脚本和导入任务不依赖 HTTP ContextVar；这些场景显式传入 locale 或使用默认 `zh-CN`。

### 7.2 Header 安全限制

语言头解析必须限制输入：

```text
最大长度。
允许字符集。
支持语言白名单。
非法 q-factor 直接忽略。
无法解析时 fallback zh-CN。
```

不要把任意 header 原文写入日志、缓存 key 或数据库。日志记录归一化后的 locale 即可。

### 7.3 后端 messages catalog

后端建立系统消息 catalog，用于通用错误、业务错误和 validation 兜底消息。

建议结构：

```text
app/platform/i18n/messages/
  zh-CN.json
  en-US.json
  fr-FR.json
  es-ES.json
  ja-JP.json
```

覆盖范围：

```text
通用错误
认证错误
参数校验错误
Agent 错误
数据集错误
评测错误
排行榜错误
后端业务 warning
评测进度说明
```

早期使用 JSON catalog 即可；消息复杂度显著上升后，再评估 gettext/Babel 或 TMS。

### 7.4 错误响应双轨协议

当前后端统一响应为 `{ code, data, message }`。国际化后，错误对象应同时提供稳定结构和本地化兜底：

```json
{
  "code": 40410,
  "message": "Dataset not found.",
  "data": {
    "status": "DATASET_NOT_FOUND",
    "errorKey": "errors.dataset.notFound",
    "params": {
      "datasetId": "A1_identity_leakage"
    }
  }
}
```

规则：

- `message` 是后端按 `contentLocale` 生成的兜底展示文本。
- `code`、`status`、`errorKey` 是稳定字段，用于程序判断、日志排查和前端二次渲染。
- `params` 是扁平标量字典，只允许 string、number、boolean、null，不允许嵌套对象。
- 前端优先使用当前 `displayLocale` 的 `errorKey + params` 渲染；本地缺 key 时展示后端 `message`。
- 网络错误或非预期结构使用前端 `network` 兜底文案。
- 业务逻辑只看 `code`、`status`、`errorKey`，禁止解析 `message` 文本。

这种设计兼顾后端新增错误时旧前端仍能展示可读文本，以及前端在具体页面中做更贴合 UI 语境的表达。

### 7.5 成功响应

后端成功响应可以保持稳定技术值：

```json
{
  "code": 0,
  "data": {},
  "message": "success"
}
```

“保存成功”“提交成功”“删除成功”等操作反馈由前端根据操作结果显示本地化 Toast，不依赖后端成功 message。

## 8. 数据库与官方元数据策略

### 8.1 数据分级

| 类型         | 示例                                                   | 翻译策略                |
| ------------ | ------------------------------------------------------ | ----------------------- |
| 系统枚举     | `running`、`completed`、`failed`、`active`             | 前端语言包翻译 label    |
| 官方领域内容 | 风险分类、风险子类、数据集名称、资产类型、攻击投递类型 | Git 翻译源 + 后端翻译表 |
| 用户生成内容 | Agent 名称、用户描述、任务说明                         | 不翻译，按原文展示      |
| 原始证据     | Agent 响应、Oracle 输出、events、visible_text          | 不翻译、不改写          |

### 8.2 核心实体使用翻译表

核心业务实体采用主表 + 翻译表：

```text
主表：稳定 code、关系、排序、启用状态、审计字段。
翻译表：locale 相关 name、description、meaning 等展示字段。
```

适用对象：

```text
dataset_sources
risk_categories
risk_subtypes
asset_types
attack_delivery_types
risk_subtype_display_meta
```

翻译表基础约束：

```text
locale NOT NULL。
locale CHECK IN ('zh-CN', 'en-US', 'fr-FR', 'es-ES', 'ja-JP')。
UNIQUE(entity_id, locale)。
外键 ON DELETE CASCADE。
常用查询字段建立 index(locale, name) 或 index(entity_id, locale)。
```

如果核心元数据存在历史引用，不应随意物理删除主表实体。更推荐使用 `is_deprecated` 或 `is_active` 标记，保持历史报告和历史任务可追溯。

### 8.3 富展示字段

以下低频结构化展示字段可以放在翻译表 JSONB 字段中：

```text
highlights
scenarios
resources
media
```

规则：

- 纯展示且不参与检索时可以保持 JSONB。
- 未来需要搜索、排序或统计时，应拆表或增加合适索引。
- JSONB 字段如进入检索路径，需要明确 GIN 索引和 locale 查询条件。
- 翻译内容入库前必须做结构校验和 URL 安全校验。

### 8.4 Git 翻译源与数据库投影

官方业务翻译源由 Git 管理，数据库是运行时查询投影。

推荐目录：

```text
data/metadata/i18n/
  risk_categories.zh-CN.json
  risk_categories.en-US.json
  risk_categories.fr-FR.json
  risk_categories.es-ES.json
  risk_categories.ja-JP.json
  risk_subtypes.*
  dataset_sources.*
  asset_types.*
  attack_delivery_types.*
  display_meta.*
```

Importer 规则：

- 使用事务包裹整个同步过程。
- 使用 Upsert 写入翻译表。
- 翻译表只做 Upsert，不因 Git 删除词条而物理删除历史实体。
- 删除或废弃官方实体通过 `is_deprecated` / `is_active` 表达。
- 任一语言导入失败必须回滚整个事务，避免部分语言成功、部分语言失败。
- 导入完成后生成差异报告，包括新增、更新、缺失和危险内容。

### 8.5 fallback 与迁移

当前主表已有中文展示字段，迁移时保留旧字段作为兼容 fallback。

fallback 顺序：

```text
目标 locale 翻译
> zh-CN 翻译
> 主表旧中文字段
> 稳定 code
```

迁移阶段：

```text
新增翻译表。
回填 zh-CN 翻译。
导入 en-US / fr-FR / es-ES / ja-JP。
服务层优先读翻译表。
记录缺失翻译指标。
稳定后弱化旧字段。
生产成熟后再清理冗余字段。
```

## 9. 数据集、评测、报告与导出策略

### 9.1 数据集展示内容本地化

数据集展示内容参与国际化：

```text
数据集名称
风险分类名称
风险子类名称
数据集简介
数据集详情
highlights
scenarios
resources label
media title
media description
```

这些内容按当前 `contentLocale` 返回。

评测样本内容不参与界面国际化：

```text
user_goal
attacker_goal
注入文本
任务 payload
网页任务内容
原始输入
执行证据
Agent 原始响应
Oracle 原始输出
```

用户切换界面语言，只改变数据集展示名称和说明，不改变样本 payload。用户不能按样本语言筛选数据集，数据集是否可用也不受用户界面语言影响。

### 9.2 评测核心固定

安全评测平台必须保证同一 Agent、同一数据集、同一配置下的评测结果不因 UI 语言变化而变化。

当前大模型判定模块使用固定 system prompt、固定 required output schema、固定 JSON 字段和固定 status。判定输出是结构化结果，不是前端 UI 文案。

规则：

```text
评测 Prompt 不随 displayLocale 改变。
判定 schema 不随 displayLocale 改变。
输出字段名不翻译。
status/code 不翻译。
内部解析逻辑不受 UI 语言影响。
```

需要本地化的是平台展示层对结构化结果的标签、说明和风险分类解释，不是判定模块本身。

### 9.3 评测记录与详情按当前语言展示

应随语言变化：

```text
页面标题
按钮
筛选项
状态标签
表格列名
数据集名称
风险分类名称
风险子类名称
图表标题
图例
tooltip
报告分区标题
状态说明
错误 message
```

不随语言变化：

```text
evaluationId
runId
sampleId
datasetId
Agent 名称
用户填写的 Agent 描述
用户输入的任务说明
Agent 原始响应
Oracle 原始输出
events.jsonl 原始事件
URL
文件名
provider 名称
模型名
错误 code/status
evidence event_id
```

当前后端 `build_status_text()` 返回中文状态说明，后续应改为以下任一方案：

- 短期：后端按 `contentLocale` 返回本地化 `statusText`。
- 中期：接口增加 `statusMessageKey` / `statusMessageParams`，前端按 `displayLocale` 渲染。

### 9.4 报告保存事实，展示时 enrich

报告数据应优先保存结构化事实：

```text
categoryCode
datasetCode
sampleId
score
count
status
outcomeCode
timestamp
raw evidence
evidence event_id
```

避免长期依赖：

```text
categoryName
datasetName
中文 summary
中文 finalizationReason
中文 statusText
```

当前 `run_reports.summary_json.byRiskCategory[].name` 属于固化展示文本，应逐步降级为兼容字段。新接口返回时应通过 `categoryCode` 按当前 `contentLocale` enrich 名称。当前 `run_datasets.dataset_name` 也应降级为兼容字段，展示时优先通过 `dataset_code` 关联翻译表获得当前语言名称。

### 9.5 导出与实时事件

当前 `run_reports.report_uri` 是预留字段，在线报告以 `summary_json` 展示为主，不设计多语言 PDF 版本。

当前策略：

```text
在线报告页面按当前语言动态展示。
report_uri 保持预留字段。
当前不设计 exportLocale。
当前不设计多语言 PDF 版本。
```

未来如果生成单一静态报告文件，应明确它是固定语言的归档资产。未来支持多语言导出时，应在导出任务或报告资产表中增加 locale，而不是把 UI 当前语言写入评测任务主流程。

如果后续增加 WebSocket 或站内实时通知，应发送结构化事件，不发送翻译后的文本：

```json
{
  "event": "EVALUATION_COMPLETED",
  "resourceId": "eval_xxx",
  "timestamp": "2026-05-09T13:55:40Z",
  "payload": {
    "status": "completed"
  }
}
```

前端根据当前 `displayLocale` 渲染 Toast 和提醒。邮件、Webhook、飞书、钉钉等离线媒介按用户偏好或任务请求快照渲染最终文本。

## 10. 缓存与性能策略

### 10.1 缓存分层

后端缓存不应简单复制完整多语言响应，应拆分为：

```text
事实数据缓存：不带 locale，保存结构化事实、统计值、ID、code。
翻译字段缓存：带 locale，保存 name、description、label。
最终响应缓存：必要时带 locale，只用于热点页面或昂贵聚合。
```

推荐将同一业务对象的多语言缓存放在同一 Redis Hash 或同一版本命名空间中，失效时一次性删除整组语言缓存，避免只清理中文缓存导致其他语言继续展示旧内容。

示例：

```text
Key: dataset_catalog_i18n
Field: zh-CN / en-US / fr-FR / es-ES / ja-JP
Value: locale-specific catalog JSON
```

### 10.2 热点预热

| 数据         | 策略                    |
| ------------ | ----------------------- |
| 数据集目录   | 预热 5 种 locale        |
| 风险分类     | 预热 5 种 locale        |
| 排行榜       | 事实缓存 + 翻译缓存组合 |
| 私有评测详情 | 按需组装，不无脑预热    |
| 大型报告     | 保存事实，展示时 enrich |
| 低频详情     | 可直接查询，但禁止 N+1  |

### 10.3 避免 N+1 查询

翻译表会增加关系查询，必须从 repository 层防御 N+1。

规范：

```text
目录类接口批量加载翻译。
详情接口一次性加载需要的翻译。
报告接口按 code 批量 enrich。
排行榜按所需实体批量查询翻译。
禁止在循环中逐条查询 translations。
```

SQLAlchemy 可使用 `selectinload`、批量 join 或 repository 级批量映射，避免在循环里访问懒加载关系触发大量 SELECT。

## 11. 安全与可观测性

### 11.1 翻译内容默认不可信

以下内容都视为不可信输入：

```text
数据库翻译字段
metadata 翻译文件
外部导入内容
后台编辑内容
LLM 生成翻译
```

前端默认使用文本插值，禁止直接对翻译字段使用 `v-html`。如确需富文本：

```text
使用受控 Markdown。
使用 HTML 白名单 sanitizer。
限制允许标签和属性。
禁止 javascript: URL。
禁止内联事件处理器。
```

后端入库前校验结构、长度、URL 协议和允许字段。错误消息不得泄露内部栈、SQL、密钥、路径和运行时环境细节。

### 11.2 原始证据不可改写

原始证据不翻译、不重写、不格式化为另一种语言。平台可以在其上方提供本地化解释性标签、字段名、状态和风险分类说明，但不能替换原文。

### 11.3 日志与监控

后端日志、错误监控和审计日志应记录稳定 code、status、errorKey、异常类型和上下文 ID，不应把本地化 message 作为主要排查依据。

前端错误上报应附带：

```text
displayLocale
timezone
route
language pack version/hash，可选
```

这有助于排查特定语言包缺失 key、占位符错误、字体问题、布局溢出和图表 locale 残留。

## 12. 翻译质量治理与 CI

### 12.1 术语表

建立统一术语表，至少包含：

```yaml
doNotTranslate:
  - AEGIS
  - Agent
  - API
  - Docker
  - Oracle
```

术语表还应包含：

```text
推荐译法
禁用译法
待确认术语
大小写规范
占位符规范
业务域归属
```

### 12.2 硬编码扫描

不建议只用全局正则扫描整个仓库，因为注释、测试、console、mock 容易产生大量误报。

推荐建立 ESLint 自定义规则或 AST 扫描：

```text
扫描 Vue template 中的用户可见 VText。
扫描 template 表达式中的用户可见字符串。
扫描 script/setup 中赋给 UI 配置、表单规则、toast、chart option 的字符串 literal。
允许注释、测试快照、debug/log 白名单。
命中用户可见中文硬编码时阻断提交。
```

### 12.3 key 与占位符检查

以 `zh-CN` 为 schema 主语言，提取所有消息 key 和占位符集合。其他语言必须满足：

```text
key 集合完整。
占位符集合一致。
HTML tag 成对且结构一致。
ICU 分支语法合法。
危险 URL 和危险 HTML 被拒绝。
```

示例：

```text
zh-CN: 评测 {agentName} 共耗时 {duration}
en-US: Evaluation of {agentName} took {duration}
```

如果目标语言缺少 `{agentName}` 或把 `{duration}` 写成 `{time}`，CI 阻断。

### 12.4 Ghost Key 与 Orphan Key

```text
Ghost Key：代码使用但语言包不存在，必须阻断。
Orphan Key：语言包存在但代码未使用，初期 warning，定期清理。
```

Orphan Key 不建议每次提交阻断，避免降低开发效率。可以通过定期任务生成清理 PR。

### 12.5 伪本地化

前端提供 pseudo locale，用于发现：

```text
硬编码中文
按钮撑爆
表格列宽不足
卡片布局溢出
图表 tooltip 截断
字体缺字
字符串拼接
```

伪本地化规则：

```text
拉长文本 30%-50%。
添加边界标记。
替换重音字符。
保留占位符。
保留专有名词。
```

### 12.6 LLM 翻译边界

LLM 可作为翻译初稿工具，但不能自动上线。要求：

```text
必须输入术语表。
必须保留占位符。
必须保留专有名词。
必须通过 CI。
必须经过 review。
安全报告、风险描述、Oracle 相关说明重点复核。
```

## 14. 验收标准

达到以下状态时，国际化主线可认为完成：

```text
URL 中语言明确，刷新和分享链接后语言稳定。
用户切换语言后，平台 UI、数据集展示、错误消息、评测状态、报告展示和图表文案切换到目标语言。
接口字段结构、enum、ID、code、status 保持稳定。
评测样本、Agent 原始响应、Oracle 原始输出、事件日志和评测结构化结果保持不变。
同一 Agent、同一数据集、同一配置下的评测结果不因界面语言变化而变化。
前端语言切换无 key 闪烁、无旧语言残留、无图表内置文案遗漏。
后端本地化上下文在并发请求中隔离，不出现跨用户语言污染。
官方业务内容可通过翻译表按 locale 查询，缺失时按规则 fallback。
缓存失效能覆盖全部语言维度，不出现某些语言展示旧内容。
CI 能阻断用户可见中文硬编码、缺失 key、占位符不一致、危险 HTML/URL 和专有名词误翻译。
法语、西语长文本不破坏布局，日语字体和断行可接受，IME 输入不受实时校验干扰。
```
